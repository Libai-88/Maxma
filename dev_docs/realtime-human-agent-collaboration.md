# 人机实时协作方案

## 目标

把一次 Agent 任务拆成三个连续阶段：执行前对齐目标，执行中允许用户纠偏，执行后由用户验收并决定是否修订。每个阶段只引入能改变下一步行为的交互，避免把用户变成提示词工程师。

## 三阶段模型

### Brief

`task-brief` 读取原始请求，在信息不足以可靠执行时提出少量澄清问题；信息足够时生成执行提示。用户可以继续回答、使用生成的执行提示，或直接使用原始请求。澄清不是审批，也不代替执行阶段的用户决策。

### Live steering

执行期间提供两种明确语义：

- `steer`：立即改变当前任务方向。Pi 在当前工具调用完成后、下一次模型调用前处理。
- `follow_up`：保留当前步骤，要求当前回合结束后继续处理补充要求。

消息只在活跃回合中接受，长度限制为 4000 字符。服务端通过 `collaboration_update` 回报入队或失败，不把失败静默成成功。

### Review

非取消回合产生最终回答后发送 `task_review_update(available)`。用户可以接受结果，或提交反馈开启新的普通回合；修订回合继续使用同一会话上下文，并重新进入验收状态。空回复、取消和错误回合不创建验收入口。

## 状态与事件

```text
brief: thinking -> clarify | ready | fallback
turn: idle -> running -> completed | cancelled | error
review: none -> available -> accepted
review: available -> revising -> available
```

回合事件按 `turn_id` 归属。`done` 先闭合回合，随后发送 `task_review_update(available)`；前端允许验收事件在已结束回合过滤器之外到达。实时协作消息不创建独立回合，修订反馈才会创建新回合。

## 失败与边界

- 重复的 `client_msg_id` 在成功回合登记后忽略，避免重试重复执行。
- 新任务、验收接受、验收修订、连接全部断开都会清理旧的验收入口。
- 最后一个 WebSocket 连接断开时取消在途回合；重新连接不会恢复已取消的回合。
- `steer`、`follow_up`、`task_review` 只能影响当前会话，不能绕过工具审批、权限模式或 MaxmaBlocker。
- 消息内容按服务端长度上限截断；空消息、无活动回合的协作消息和无效验收动作被忽略。
- 当前验收状态为后端内存态，进程重启后不恢复未完成的验收入口；会话消息仍以会话存储为准。

## 评估指标

- 首次成功率：无需修订即被用户接受的回合比例。
- 用户纠正率：执行中发送 `steer` 或 `follow_up` 的回合比例。
- 过度提问率：澄清后仍被用户立即纠正的回合比例。
- 修订率：进入 `revising` 的已完成回合比例。
- 额外延迟：澄清、实时协作和修订带来的额外端到端时间。

模型自报的 confidence 只作为界面线索，不当作校准概率，也不单独决定是否执行或提问。
