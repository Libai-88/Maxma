# 发布说明

适用于发版前整理变更、或把一长串提交记录变成用户能读懂的更新日志。

## 取材

1. `git log <上一个版本标签>..HEAD --oneline --no-merges` 取原始提交；有 tag 就用 tag，没有就用上次发布日。
2. 按目录或提交前缀粗分类（`feat` / `fix` / `perf` / `docs` / `chore`），再看 `git show --stat` 确认**实际改了哪些文件**——提交信息可能写得比改动大。
3. 涉及用户可见行为时，回到代码或测试确认口径；拿不准的写成"待确认"，不要替作者总结。

## 写法

分四块，顺序固定：

- **新增**：用户能感知的新能力，一句一条，说清"现在可以做什么"。
- **修复**：先写症状（用户看到什么），再写结果，不写内部实现。
- **变化 / 移除**：会影响既有用法的地方必须显眼，注明迁移方式。
- **内部**：测试、构建、文档、依赖，合并成一两条即可。

每条控制在 60 字内，动词开头；不复制提交原文，不写"优化了若干问题"这类空话。破坏性变更单独列出并给出替代做法。

## 边界

- 不把重构、格式化、注释清理写进"修复"。
- 没有证据的收益（"性能提升 30%"）不要写；要写就附测量方式或测试结果。
- 发布说明面向使用者：内部代号、工单号只在括号里出现。
